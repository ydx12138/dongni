# PC 单点登录设计

## 目标

PC 网站同一普通用户账号只允许保留一个有效登录会话。用户在另一台 PC 设备重新登录后，旧设备下一次访问需要登录的接口时，后端返回专用业务码；PC 前端清理本地登录状态并退出。

## 范围

- 仅处理 PC 网站的邮箱密码登录、Token 刷新和普通用户鉴权。
- 管理员登录与管理员鉴权保持现状。
- 微信小程序不在本次修改范围内，不修改其代码、交互和既有登录行为。
- 不改动数据库表结构。

## 会话数据

PC 邮箱密码登录成功后，Service 使用密码学安全随机数生成 `session_id`。

- access token 和 refresh token 的 JWT Claims 均包含 `session_id`。
- Redis 使用键 `pc:user:session:{userID}` 保存当前 `session_id`。
- Redis 过期时间为 7 天，与 refresh token 保持一致。
- 同一账号再次从 PC 登录时，新 `session_id` 覆盖旧值，旧 Token 不再通过校验。

## 后端流程

1. `UserLogin` 查询用户、校验密码和用户状态。
2. Service 生成 `session_id`，签发携带该字段的 access token 与 refresh token。
3. Service 将 `session_id` 保存到 Redis；Redis 写入失败则不返回登录成功。
4. `JWTAuth` 解析 access token。仅当 Claim 中存在 `session_id` 时，通过 `redisMiddleRepo` 获取 Redis 中的当前会话并比较。
5. Redis 会话不存在或与 Token 中的值不同，鉴权中止并返回业务码 `1008`，消息为“账号已在其他地方登录”。
6. Token 刷新接口对携带 `session_id` 的 refresh token 执行相同校验；校验成功后，新 access token 复用该 `session_id`。

微信小程序既有 Token 不携带 `session_id`，因此不进入本次新增的 PC 会话对比逻辑。

## Repository 边界

`internal/repository/redis_middle_repo.go` 负责 Redis 会话读写；`RedisMiddleRepository` 暴露保存与读取当前会话的方法。`internal/middleware/auth.go` 只依赖该接口，不直接操作 Redis 客户端。

## 前端流程

1. PC 前端登录后读取后端返回的 `access_token`，保存为 `blog-token`。
2. 请求层收到业务码 `1008` 时，删除 `blog-token` 和 `blog-user`，并派发浏览器事件。
3. `auth` store 监听该事件，清空内存中的响应式用户状态；页面立即显示未登录状态。
4. 请求层向调用方抛出可识别的错误，页面可按既有错误展示方式提示“账号已在其他地方登录”。

## 错误处理

- Redis 操作异常：鉴权返回现有服务器内部错误，避免在 Redis 不可用时放行未知会话。
- 会话不匹配或已过期：返回 `1008`，前端退出登录。
- Token 缺失、签名无效或 access token 过期：保留现有响应码与处理逻辑。

## 验收

- 同一账号在 PC A 登录后可访问需要登录的接口。
- 同一账号在 PC B 登录后，PC A 的下一次鉴权请求返回 `1008`，并被前端清理登录态。
- PC B 仍可正常访问和刷新 Token。
- 管理员登录及微信小程序既有流程不受影响。
